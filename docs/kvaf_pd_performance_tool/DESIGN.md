# KVAF PD 性能分析与阶段耗时可视化工具设计

版本：v1.7 请求预热识别与正式请求筛选增补稿。日期：2026-11-13。

状态：以已确认的 v1.6 为基线，按用户本轮指示增加请求预热识别及仅正式统计。用户已授权实现，当前本地进展见 [实现记录](IMPLEMENTATION_STATUS.md) 与 [开发计划](DEVELOPMENT_PLAN.md)。不提交或推送。
本文定义目标契约，不表示所有目标已完成；实现记录逐项区分已验证能力和待接入观察点。

## 1. 目标与边界

在已有真实 PD 推理测试中，用可插拔的低开销采样器记录请求发出后的执行过程，离线生成类似算子 Profiler 的可交互时间轴阶段耗时报告。
重点解释 PD Connector 的信息交互、排队、两条 KV 传输路径、完成门控对推理性能的影响。

沿用已有部署和请求发送工具；工具不生成请求，不自动修改模型、并行、图模式或发送负载。
输入长度、目标输出长度、D 每卡目标 batch 均可配置，报告同时展示配置目标和实际观测值。
日常分析在服务所在容器或服务器的终端执行独立脚本，直接显示统计；需要阶段耗时时汇总导出一个 Trace 文件，复制到 Windows 可视化。
Windows 查看器不依赖 NPU/SDK，不连接推理服务，不要求部署常驻 Web 服务。

工具唯一的性能分析对象是**用户发送的真实推理请求**。主线为请求发送 → 路由/排队 → D 请求 block 分配/绑定 → P Prefill → Connector 交互与 KV 传输 → D Decode → 输出接收完成。
该主线表达阶段范围，不规定实际执行必须串行；时间轴按真实事件展示先后、重叠及等待。

所有性能事件必须属于用户实际发出的推理请求，并有可核对的请求 ID、代次或共享 batch membership。
无请求归属的事件不形成性能样本；缺少客户端记录时，从可证实的请求接收点展示局部跨度，不向前扩展边界。

**范围排除：实例启动与初始化完全不属于本需求。** 模型加载、通用 HBM/DDR 内存池预分配、MR 注册/导入、
通信建链/探测、图捕获及实例预热，不采集、不计时、不统计、不绘图，也不纳入开发任务和性能验收。
不设置上述阶段的 hook、事件名、计时字段、开关或报表；不从相关日志或历史事件反推请求阶段。

仅保留已接收请求从既有资源池分配或绑定 D block/接收容量的业务耗时，必须关联到本请求；
它表示该请求取得资源的过程，不表示创建资源池或注册内存。
进程代次、已有资源身份、静态配置和时钟映射只作为关联元数据读取，不生成额外性能阶段。

### 1.1 已确认的实现契约

| 问题                   | 唯一解释                                                                                                             |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 分析什么               | 请求阶段、请求里程碑以及这些事件所属的时间域                                                                         |
| 正式统计包含哪些请求   | 仅有显式 measure 证据的请求；请求预热、探针、profiling 和未知用途默认排除，详见第 3.5 节                             |
| 如何判定事件在范围内   | 真实请求已发出，事件属于第 5～6 节允许的请求阶段，且可关联到请求 ID 或其共享 batch；仅发生在采集窗口内不构成纳入理由 |
| 最关注什么             | PD Connector 信息交互/等待、t1/t2 数据传输及其对请求响应的影响                                                       |
| 图上画什么时间         | 每个真实请求中实际发生的阶段跨度，不用平均值或 P99 拼接假时间线                                                      |
| 汇总用什么指标         | mean、P90、P99、有效 N 同时输出，不只选其中一种                                                                      |
| “请求层样本”是什么     | 一个请求在一个模型层上的某条路径合并耗时，分段合并后只算一个样本                                                     |
| “请求累计”是什么       | 一个请求该路径所有有效层的耗时之和，不等于请求端到端墙钟时长                                                         |
| 输入/输出/batch        | 目标可配置，实际观测单列；不由统计工具发送或修改负载                                                                 |
| 工具形态               | 可插拔采样、离线分析、类似算子 Profiler 的交互阶段耗时和统计面板                                                     |
| 服务侧如何看结果       | 在服务环境中单独运行分析脚本，终端直接显示统计，不在推理进程内同步分析或绘图                                         |
| Windows 如何看阶段耗时 | 将所选请求的事件、关联、摘要和时钟信息汇总到一个 Trace 文件，复制后由离线查看器打开                                  |
| 采集开销怎么控制       | 采样率、详细级别、事件缓冲和后台写盘均可配置；超限不阻塞推理，配置及丢样情况随报告保存                               |

需求解释以本契约及第 5～9 节为准。实现核对只落实观察点与能力缺口，不自行扩大性能采集范围或更换统计口径。

## 2. 实验拓扑与负载

| 角色 | 当前目标配置                                             |
| ---- | -------------------------------------------------------- |
| P    | 一台八卡 A，TP8 / DP1 / EP8                              |
| D    | 一台八卡 A，TP1 / DP8 / EP8                              |
| K    | 两台鲲鹏，合计四个 CPU/socket 服务；每服务对应两个 D NPU |

P `.12`、D `.24`、K `.71/.73` 是现有部署实例，不写死在通用分析逻辑中。
报告读取实际物理 NPU→K endpoint 映射，以及 source_tp0_only 等运行配置；不改变其取值。
既支持当前 TP0-only 采集，也为其他实际贡献者保留请求关联身份；未实测组合明确标记。

负载参数含义如下，分析配置不负责改变服务端或发送端实际配置：

| 参数             | 已讨论的示例目标 | 实际证据                                                  |
| ---------------- | ---------------- | --------------------------------------------------------- |
| 输入 token       | 131072，可修改   | 原生请求元数据或发送工具导出的实际 token 数               |
| 输出 token       | 125，可修改      | 实际输出数、finish_reason；未导入则标未知                 |
| D 每卡逻辑 batch | 16，可修改       | 每 DP 的真实调度批次，不以 max-num-seqs 或图 padding 替代 |
| 请求数、并发     | 外部发送工具控制 | 本轮请求 ID 集合、发送窗口和成功状态                      |

输入 131072 加输出 125 已超过旧 max-model-len=131072，实验前需核算总长度及 MTP 余量。
batch=16 需相应 max-num-seqs、足够并发及 HBM/DDR 容量；每卡 DDR=16 GiB 不能自动当作该负载的足够预算。
工具记录这些前提，不擅自提升配置或承诺目标 batch 必然达到。

## 3. 硬性要求：性能、精度与日志

### 3.1 原推理行为保持

1. 不改变模型权重、KV 内容、Tensor 布局、有效长度、block 映射、采样和 MTP 状态。
2. 不新增 KV payload 拷贝、哈希、Tensor 回读、设备标量读取或采样专用 HBM workspace。
3. 不新增设备同步、barrier、控制 RPC、SDK READ、事件轮询线程或业务重试。
4. 原调用按原参数和顺序执行，原返回、业务异常、恢复、ACK、Commit 和释放语义保持。
5. 不以埋点成功作为任务完成依据，不增加业务锁的持有时间或让采样锁参与资源调度。
6. 不为了 trace 保留 Tensor、Ready、Put、stream 或其他设备资源引用，避免改变其释放时机。
7. 采集器自身故障不覆盖原异常、不令成功推理失败、不令失败推理变成成功；分析结果显式标记缺失。

硬件调用的完成以原路径已经确认的状态为准。包装函数内的业务异常和采集异常分开处理，不能用宽泛异常处理吞掉业务错误。
配置及容量校验优先在离线预检查完成；运行中采集故障按声明策略停止采集或丢弃样本，原推理继续按原语义执行，不静默切换详细级别或采样率。

### 3.2 开销与日志上限

热路径仅收集必需的单调时间、已有身份和小型标量元数据；序列化、统计、排序和文件写入由后台或离线完成。
使用有界非阻塞队列、事件/字节预算、文件大小预算；缓冲超限按配置丢弃采样或停止采集并计数，不反压推理。
文件按配置大小分片，总写盘预算耗尽后停止本进程本轮采集，不能覆盖仍需统计的历史事件。

以完整请求为采样选择单位，尽量避免只采部分层；按请求、层、chunk 和路径控制粒度。
原始事件文件与控制台日志分开，禁止逐层逐 RPC 打印 Info/Debug；仅保留采集配置摘要、限频故障和结束摘要。
请求选择、采样率、详细级别、队列/文件上限和批量 flush 策略统一按第 3.3 节配置，不散布新环境变量。

采样率、详细级别、缓冲和写盘都有成本，不能承诺无条件零开销。
性能影响通过同负载 A/B 对照量化；性能、内存和精度门槛作为本轮实验元数据保存，未填写或未实测时不宣称验收通过。

### 3.3 可配置采集契约

以下定义目标配置及设计默认值；第一批字段支持情况以实现记录为准，不表示所有观察点已接入，也不表示默认开销已通过实测。
采用工具专用 JSON 文件 `kvaf_pd_performance.json`，默认与采样模块同目录；路径在采样模块原有集中配置区指定，支持绝对路径。
由显式选择的采样插件读取，不向原生 `additional_config` 或 `kv_connector_extra_config` 追加未知参数，不修改业务 `kvaf_config`。
不新增原生 CLI 或环境变量，不设置多套优先级；配置文件为唯一值来源，未填写的字段使用本节默认值。
配置文件缺失时保持采集关闭；各 P/D 进程使用可访问路径。第一批已落地字段解析，实际约束与尚未接入的细节见实现记录。

| 配置项                     | 建议默认值    | 范围与作用                                                                                                 |
| -------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------- |
| `enabled`                  | `false`       | 布尔；采集总开关，与显式选择采样 Connector 同时满足才生效                                                  |
| `sample_rate`              | `0.1`         | 有限数值 `[0,1]`；按请求选择，`0` 不采集，`1` 选择全部符合条件的请求                                       |
| `sample_seed`              | `0`           | 整数 `[0, 2^32-1]`；使用稳定请求关联键进行可复现的采样选择                                                 |
| `detail_level`             | `"layer"`     | `stage`、`layer`、`detail`；控制事件粒度，不改变推理参数或控制台日志级别                                   |
| `buffer.max_events`        | `2048`        | 正整数；每进程队列中可驻留的事件数量上限                                                                   |
| `buffer.max_bytes`         | `16777216`    | 整数，至少 32768，默认 16 MiB；每进程待处理事件及关联记录的保守内存预算，与数量限制同时生效                |
| `buffer.overflow_policy`   | `"drop_new"`  | `drop_new` 丢弃新事件并计数；`stop_capture` 停止本进程本轮采集，均不阻塞业务                               |
| `writer.enabled`           | `true`        | 布尔；控制原始事件、manifest 和 checkpoint 的文件写入，不代表采集总开关                                    |
| `writer.output_dir`        | `"./pd-perf"` | 非空路径；相对路径以进程工作目录为基准，按 run/进程划分独立目录，供本地分析和 Trace 汇总，不覆盖旧数据     |
| `writer.batch_events`      | `256`         | 正整数且不大于 `buffer.max_events`；后台批量处理/写入的事件数阈值                                          |
| `writer.flush_interval_ms` | `5000`        | 正整数毫秒；即使事件未满批量，也按间隔提交已缓冲数据及完整性计数                                           |
| `writer.file_buffer_bytes` | `1048576`     | 整数，至少 2，默认 1 MiB；每进程文件 I/O 缓冲预算，独立于事件队列预算                                      |
| `writer.max_file_bytes`    | `67108864`    | 整数，至少 131072，默认 64 MiB；单个事件分片大小上限，预留有界元数据空间，到达后创建新分片，不覆盖历史分片 |
| `writer.max_total_bytes`   | `268435456`   | 正整数，默认 256 MiB；每进程每轮全部采集文件的总上限，包含事件和有界元数据收尾空间                         |

采样选择以完整请求为单位，使用稳定算法和上述 seed；不逐层、逐 chunk 或逐次 RPC 独立随机抽样。
P/D 使用同一选择契约和可关联的请求键；不能一致关联时标记证据不完整，不将不同请求或不同端独立抽样拼成完整请求。
请求 ID 筛选先于采样比例，选择结果对该请求保持不变；共享 batch 事件仅记录一次并关联被选中的请求。
不为传播采样选择增加控制 RPC、同步或修改业务协议；可用关联键由 M1 核实。

详细级别定义如下：

| 档位     | 记录内容                                                             | 能输出的结论                                                               |
| -------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `stage`  | 请求阶段跨度、关键里程碑、时间域及实际 batch 关联                    | 阶段和可得的 E2E 分布；缺少逐层证据时不输出 t1/t2 请求层或请求累计四组结果 |
| `layer`  | `stage` 加 t1/t2 的请求/层/chunk/path/贡献者起止与完成证据           | 默认分析档，支持四组核心统计及层/chunk 阶段耗时；只收集归集必需事件        |
| `detail` | `layer` 加可观察的逐 RPC、锁/排队、SDK 调用、Commit/Publish 嵌套跨度 | 用于局部慢请求排查，事件量更大；未覆盖内部阶段仍标未知                     |

任何档位均不新增设备同步、读取 KV payload 或逐事件打印，不启用第 1 节排除的阶段。
低档缺少的指标显示 `UNAVAILABLE` 及原因，不用外层墙钟跨度代替请求累计；高档也不承诺覆盖不可见的 SDK/设备内部执行。
建议先用 `layer` 和较低采样率观察；定位指定请求时可在较短采集窗口选择 `detail`。
降低采样率会减少有效 N，不能保证获得足够的 P99 样本；报告必须展示实际比例、有效 N 和筛选/丢样情况。

缓冲、写盘与关闭行为必须满足以下约束：

1. 事件数和保守字节预算任一触顶即执行超限策略；计费使用有界记录/预留容量，不在业务线程为计费序列化或遍历对象。
2. `max_bytes` 不是整个进程 RSS 上限；文件缓冲、后台在途批次及元数据另计且必须有界。报告记录每进程配置，整机预算按采集进程数汇总。
3. 后台在批量阈值或 flush 间隔满足时写入；业务线程不等待 flush、磁盘或后台批次。flush 不等于 fsync/断电持久化保证。
4. `max_total_bytes >= max_file_bytes`；后台按实际序列化字节核算，单条记录超限也不得突破文件预算。总预算内预留有界收尾空间；磁盘失败时不能承诺最终 checkpoint 已写出。
5. 队列丢样、预算停止或磁盘错误要记录原因、计数及影响范围；不能自动覆盖、扩容、提高 I/O 优先级或反复重试写盘。被截断请求按第 7.3 节处理。
6. `writer.enabled=false` 时仅在有界内存中暂存，不创建事件/manifest/checkpoint 文件或后台写盘线程；退出不隐式落盘，只保留有限控制台计数摘要。无文件供独立脚本读取，此模式不提供终端阶段分析或 Trace 导出。
7. `enabled=false` 或 `sample_rate=0` 时，不创建 observer、采集队列、写盘线程、输出文件或专用设备资源。请求热路径只保留关闭条件判断，直接调用原操作；不读取配置、不哈希采样、不计时、不构造事件或复制采集上下文，不执行采集回调/序列化/I/O，也不增加同步、RPC、SDK 调用和重试。原操作的顺序、次数、返回值、异常及资源生命周期保持一致。
8. 每轮采集固定一份配置快照，不承诺请求中途热修改。需要调整时使用新采集轮次，不能把不同档位或采样率的数据无标识混合。

集中校验类型、有限数、范围、枚举、未知字段和跨字段约束；布尔不充当数值。离线预检查明确拒绝无效配置，不静默纠正。
若绕过预检查，插件不得以无效配置开始采集；明确记录停用原因，保留原推理行为。
报告保存有效配置、算法版本、请求选择数量、丢样计数和实际写盘量；采集参数不代替负载参数。

### 3.5 请求用途与正式统计

请求用途由发送工具声明为 `request_phase=measure|warmup|profile`；没有声明为 `unknown`。
不得根据请求名称、先后顺序、输入长度、输出数或快慢猜测用途。尤其 PD 正式请求在 P 阶段也可能只生成一个 token。
这与实例内部的 dummy forward 不同：后者仍不采集；真实 HTTP 请求预热可保留原始事件，但默认不进入正式统计和导出。

已有 benchmark 给前缀预热、prefix 探针及请求预热标记 warmup，profiling 标记 profile，普通正式波次标记 measure。
`--warmup-rounds` 和 `--warmup-batch-size` 只控制现有发送端的显式请求预热，默认 0 轮，不增加默认负载。
预热波次完成后才发送正式波次；预热失败时停止运行。支持 `--request-phase warmup` 声明预热专用运行。
这些是客户端配置，不是新增 vLLM 原生参数，也不恢复任何实例阶段计时。

HTTP 头 `X-KVAF-Request-Phase` 仅供观察插件读取，不加入模型正文或 P/D 的业务 KV 协议。
benchmark 默认只在客户端结果中保存标签，不增加请求头；显式 `--tag-request-phase` 才发送该头，避免改变默认请求格式。
Proxy 为原 API 子请求保存用途；分析以精确请求 ID/代次关联到 P/D。
不使用 Proxy 采集时，通过 `--client-records` 导入现有发送工具的标签及实际响应 ID；也接受仅含已核实 ID/代次/用途的 JSONL 清单。
仅用途清单不伪造客户端时间或 E2E。无法唯一关联的标签不传播到其他请求，来源冲突明确拒绝。

`summary` / `export-trace` 默认只分析 measure。筛选先于长度识别和聚合，覆盖四组 t1/t2、阶段分布、
客户端 E2E/TTFT、实际 batch、代表请求和 Trace membership；未知用途不因缺少正式样本而自动转为正式。
没有可确认正式请求时有效 N 为 0，并明确报告不可用于正式统计。
诊断可显式选择 warmup/profile/unknown/all；终端及查看器必须标明诊断范围，不能宣称该分位数为正式测试结果。

用途筛选不拆分共享 batch 的实际跨度。只关联所选正式成员，保留实际 batch 大小；不能按人数扣掉预热所占计算。
不能从整个采集窗口的 batch 直方图推导正式 batch 分布，需使用所选请求的实际 batch membership。
采样仍作用于真实请求，预热原始事件占用相同预算；丢样/采集故障的全局完整性约束不因用途筛选而消失。
旧的无标签记录为 unknown；历史无子命令分析/compare 仅保留兼容，不承担新版正式用途筛选。

## 5. 请求阶段、里程碑和时间域

### 5.1 请求起点与结束点

请求端到端的主定义是：**现有发送工具实际发出请求 → 客户端收到最后有效响应并确认完成**。
客户端 E2E 保留这个真实跨度，不为了只显示已覆盖阶段而扣减未知时间，也不增加范围外的阶段填满时间轴。
优先导入现有发送工具的请求 ID、发送/完成时间和输出结果；不为取得这些信息另建发送工具。
Proxy 接收 → Proxy 发出最后响应另称“服务端请求跨度”，不能替代客户端端到端指标。
若只获得引擎或 Connector 内部事件，则展示对应“局部观察跨度”，客户端 E2E 标未知，不把缺少前后阶段的时间线称为完整请求。
外部请求 ID、P/D 内部 ID 与代次必须明确关联；不按日志顺序、prompt 内容或时间接近推断同一请求。

首 token 标明实际产生端、Proxy 发出时间与客户端接收时间的可用范围。
不能假定首 token 必须由 D 首轮 Decode 产生，也不能用 HTTP 响应头返回替代首个有效输出 token。
非流式请求的客户端 TTFT 不可从整包响应时间中伪造，需服务端证据或外部工具支持。

### 5.2 请求阶段耗时

| 阶段                   | 起止边界                                                           | 备注                                                           |
| ---------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------- |
| 请求路由/排队          | 对应入口 → 获得调度/转发机会                                       | P、D、Proxy 分别保留，不强制先后                               |
| D 请求 block 分配/绑定 | 本请求 block 分配/绑定调用进入 → 该请求所需 block/接收容量结果可用 | 仅观察本请求取得既有池资源的过程，不扩展为内存池创建或 MR 注册 |
| P Prefill 主机执行     | 提交相关计算的主机调用进入 → 返回                                  | 不能直接称为 NPU 计算耗时                                      |
| P Prefill 设备执行     | 已有有效设备事件的起止                                             | 只有可无新增同步地获取证据时启用                               |
| P 发送任务等待         | 原层任务产生 → 发送线程开始处理                                    | 线程池和源组占用等待单独记录                                   |
| P 生产完成等待         | 原有生产事件等待进入 → 确认完成                                    | 不增加一次同步；不将 Host 回调等同于 KV 已生产                 |
| Connector plan/元数据  | 本请求对应控制调用发起 → 返回                                      | 请求编码、发送排队、远端处理、回执的外层跨度                   |
| D 服务端处理           | 回调进入 → 处理完成/回包交接                                       | 内部可分锁等待、wait_compute、描述符等原有动作                 |
| t1 / t2 传输           | 见第 6 节                                                          | 两条路径及其嵌套分解                                           |
| 请求接收完成汇总       | 最后必需依赖满足 → 原接收完成状态发布                              | 不等待无关 D worker                                            |
| D Decode 调度等待      | 接收完成 → 对应实际计算批次开始                                    | 与接收 gate 就绪分开                                           |
| D 计算/采样            | 各原调用及已有设备执行证据                                         | Target、MTP、实际输出/接受数可关联但不改状态                   |
| 响应返回               | 输出可用 → Proxy/客户端实际接收                                    | 可观察端点分别展示，不跨机裸减                                 |

上述为期望观察边界；具体 hook 由 M1 源码矩阵落实，未覆盖部分显示未采集。
D 请求 block 分配/绑定、P chunk 计算和逐层传输允许交错，阶段耗时按实际 span 和因果关系重建，不预设线性串行流程。

### 5.3 请求里程碑与完成依据

以下名称是拟议观测语义，不要求新建同名业务状态；通过原有调用与完成确认关联，不增加等待。

| 里程碑                           | 含义及依据                                             | 不可替代的边界                                               |
| -------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| CLIENT_REQUEST_SENT              | 发送工具实际发出请求，可由已有导出证据获得             | 没有客户端证据时保持未知，不用 Proxy 接收代填                |
| REQUEST_ACCEPTED                 | Proxy 或所选引擎实际接收请求                           | 仅见 Connector 时不能补造全局入口                            |
| D_REQUEST_BLOCKS_READY           | 本请求接收 block 和所需容量的分配/绑定结果可用         | 仅代表本请求取得接收资源，仍需等待 KV 接收门控               |
| P_PREFILL_SUBMITTED              | 对应 chunk/batch 的 P 计算已提交                       | 不等于设备计算完成                                           |
| P_SOURCE_READY_OBSERVED          | 原路径已确认所需源 KV 生产完成                         | Host 层回调不替代原设备完成确认                              |
| TRANSFER_ELIGIBLE                | 具备可观察的传输编排条件                               | 不把排队后的 RPC 开始当排队前起点，详见第 6.1 节             |
| PULL_RPC_STARTED / ACK_RECEIVED  | 真实 Pull 控制调用开始及回执返回                       | 外层跨度含控制与服务处理，不是纯 DMA                         |
| HBM_PULL_DONE                    | 原 NPU Pull 确认本次数据接收完成                       | 不是仅调用提交成功                                           |
| DDR_COMMITTED / DDR_PUBLISHED    | CPU Pull 已完成、事务已提交、可读目录已发布            | Wait、Commit、Publish 分别保存，不合成提前就绪               |
| RECEIVE_GATE_READY               | 本请求全部必需层/贡献者与两路径满足接收门控            | 不等待无关 D 请求；合法无任务/跳过单独表达                   |
| D_DECODE_STARTED                 | 实际包含该请求的首轮 D 计算开始，保留 host/device 来源 | Scheduler 放行不等于设备已经执行                             |
| FIRST_OUTPUT / REQUEST_COMPLETED | 实际首个有效输出与最终完成                             | 区分 P/D 产生、Proxy 发送及客户端接收的观察端                |
| CLIENT_RESPONSE_COMPLETED        | 发送工具确认最后有效响应接收完成                       | 结束状态、实际输出数和请求 ID 须匹配，不能以 HTTP 响应头替代 |

以消息、请求/层/chunk、贡献者和原完成依赖连接里程碑。阶段耗时必须能回答“事件已经就绪，下一步为什么还没开始”。
D 请求 block 分配/绑定和 P Prefill 的前后关系、不同层/chunk 的重叠均按真实事件呈现，不按上表顺序人为串行化。

### 5.4 请求时间域与展示规则

| 时间域                | 允许表达的内容                           | 限制                                                  |
| --------------------- | ---------------------------------------- | ----------------------------------------------------- |
| 客户端                | 发送工具导出的 E2E、实际输出和可得 TTFT  | 需可关联的请求 ID；没有导出时标未知                   |
| Proxy / 引擎          | 对应入口到输出、路由和调度等待           | 起点和结束点保留所在观察端，不混成客户端 E2E          |
| P/D Host              | 本机调用、排队、锁等待、RPC 及完成确认   | 本机单调时钟计算持续时间，不把异步返回当计算完成      |
| NPU device            | 已有且可无新增同步取得的设备执行证据     | 与 Host 分列，未校准时不直接投影成精确统一时间轴      |
| K endpoint 调用方观察 | P/D 所见的 SDK/控制跨度及相应 K 路由     | 无 K 内部事件时不标为 K 纯执行时间                    |
| 跨主机对齐            | 有同步证据的相关事件，或带误差的因果近似 | 不直接相减不同主机 monotonic 时间，不伪造单向网络时延 |

每个 span 和里程碑带观察端、时钟域及计时依据。展示实际持续时间与不确定对齐信息，详细时钟契约见第 8.2 节。

### 5.5 设备计算和共享 batch

默认低开销档使用主机时间及原本已发生的完成确认，不新增 NPU event、同步或轮询。
原有设备证据可读取时另标 device 时间，保留设备时钟域，未校准时不与主机时间轴直接相减。
主机发起和返回跨度不当作纯设备执行时间；没有设备计时时将该指标标为不可用。

每个计算 batch span 只保存一次，通过 membership 关联多个请求；不能机械除以 batch 得到“每请求计算耗时”。
请求各自的等待经历可以包含同一个共享 batch，但统计全局资源占用时去重。
记录实际逻辑 batch、调度 token 数、有效 token 与可得的图 padding；不将 padding 数当实际 batch。
实际 batch 最好能按请求关联到各次调度，不只保留全运行窗口的直方图。

## 6. 双 Pull 与 Connector 开销分解

| 路径 | 数据方向与内容                                                 | 成功条件                             |
| ---- | -------------------------------------------------------------- | ------------------------------------ |
| t1   | P HBM → D HBM；Indexer、Scale、主 KV tail 及实现实际归属的数据 | 原 NPU raw READ 确认完成             |
| t2   | P HBM → K DDR；完整块主 KV                                     | CPU Pull 完成，Commit 与目录发布完成 |

### 6.1 用户口径与现有计时器的区别

用户目标是“传输允许发起 → Pull 确认完成”，包含期间的接口、排队、控制等待。
主统计边界优先使用 P 侧同一主机时基：P 观察到该传输可编排 → P 收到相应成功完成回执。
t1 回执必须对应 NPU Pull 完成，t2 回执必须对应 CPU Pull 完成且 Commit/目录发布已完成；同时保留 D 侧内部完成里程碑供分解。
这样主指标保留用户关心的完成确认和控制等待，不用跨机未校准时间相减计算。
现有工具只测 P 的 op=pull RPC 发起至成功回执，排除了更早的发送线程等待、生产等待及 plan RPC。
保留已有值为 `pull_rpc_ms` 兼容指标，不将其静默改名为完整用户口径。

新工具增加“传输可编排/允许发起”的观察里程碑，覆盖从条件就绪到最终完成的跨度。
条件至少包含本请求相关源生产完成和本地必要业务元数据可用；不能把抢到 Runtime 锁或完成 plan 后的点当成排队前起点。
M1 要按真实代码为 t1/t2 确定可以可靠观察的边界，并说明它是主机确认时刻还是设备实际时刻。
无法精确观察时不补造时间戳，完整指标标未知，已有 RPC 指标仍可独立统计。
RPC 前公共 plan/排队可能为两路径共享，作为共享 span 保存；两路径各自经历可重叠，不能相加当总控制面成本。

### 6.2 分解层级

```text
允许编排 → 传输完成
  ├─ P 本请求发送排队/源组占用等待、plan 与 Ready 协调
  └─ Pull RPC 外层
       ├─ 控制请求编码、网络、回执及未覆盖排队
       └─ D 回调处理
            ├─ Runtime 锁与计算依赖等待
            ├─ 本次传输描述符生成与 DDR 事务处理
            ├─ SDK 调用及完成等待
            └─ Commit、目录发布及回执生成
```

CPU Prepare/Submit/Wait/Commit/Publish 可按现有调用边界观察；Submit 返回不当作搬运完成。
这些调用必须归属于本请求/层/chunk 的实际 KV 传输，Prepare 仅指本次传输事务的处理。
NPU READ 按真实同步/恢复契约确认，不新增 READ，不把控制请求已发送当作数据可用。

P RPC 时长减去其对应 D 处理时长只能得到混合残差，包含请求编码、网络、回执及回调前排队等，不能称纯网络时间。
只有身份、嵌套边界和时钟质量允许时才展示该残差；负值或不一致标为证据错误，不强行截零。
SDK span 不能继续推导为纯 DMA/纯链路带宽；需要已有内部计时才展开，传输字节/跨度所得仅为该观察口径的有效吞吐。

## 7. 样本归集与统计

### 7.1 t1/t2 四组核心结果

以下四组是 `layer`/`detail` 档的要求；`stage` 档缺少逐层证据时按第 3.3 节标记不可用，不伪造样本。

| 路径 | 样本粒度              | 输出                   |
| ---- | --------------------- | ---------------------- |
| t1   | 请求层样本（请求×层） | mean、P90、P99、有效 N |
| t2   | 请求层样本（请求×层） | mean、P90、P99、有效 N |
| t1   | 请求累计              | mean、P90、P99、有效 N |
| t2   | 请求累计              | mean、P90、P99、有效 N |

**一个请求 + 一个模型层 + 一条路径，构成一个请求层样本**，唯一身份还包括请求代次。
它不是该层中某一次 API 调用，也不是某个 TP rank、某个 chunk 单独作为最终样本。

同一请求/层/chunk/path 的并行 TP 分支按最早开始至最晚完成的整体跨度合并，不简单累加贡献者时长。
同段含多个调用时保留各调用及外层跨度，明确等待间隔是否包含；各 chunk 的合并耗时再相加得到该请求层样本，不包含 chunk 之间的其他计算间隔。
请求累计等于该路径各层样本之和，保留用户确认口径，不等于请求墙钟时间。
MTP 层、Target 层和跳过贡献要显式分类，不能因缺少某次合法跳过就错误判断丢样，也不混成同类层统计。

例如以下仅为统计口径示意，不是测量结果：请求 A 两层 t1 为 2、3 ms，请求 B 两层为 4、5 ms。
请求层统计使用 2、3、4、5 四个样本，N=4；请求累计使用 A=5 ms、B=9 ms 两个样本，N=2。
有效 N 按路径和粒度分别计数；另列有效请求数、层数及各层覆盖率，不能用预期请求数×模型层数代替实际有效 N。

P90/P99 从最终样本直接计算，采用与现有工具一致的线性插值并记录算法版本。
不先求每层 P99 再相加，不用每段分位数组装“P99 请求”。

### 7.2 其他阶段与关键路径

各请求阶段都输出 mean、P90、P99、有效 N。默认阶段汇总以“一个请求在该阶段的合并耗时”为一个样本，避免分段多的请求被重复加权。
重复阶段的合并方式必须按指标声明：可累加操作保留累计值；重叠操作另列区间并集；首尾跨度单独命名，不把三者混成一个数。
逐 RPC/操作分布作为下钻结果单独展示，样本单位标为调用，不与请求阶段分位数混用。
请求端到端直接以完整请求的发送至接收完成耗时作为样本，不由各阶段耗时或分位数相加推导。
请求汇总保留累计、区间并集和首尾跨度的区别，禁止将嵌套父子 span 重复相加。
并行传输可能被 P 计算掩盖，累计传输时间不直接等于 TTFT 或 E2E 的增加量。
以消息、生产/接收完成、batch、Commit 和调度边界构造因果依赖，证据完整时标识阻塞 Decode 的关键链。
只有本地依赖时输出局部阻塞链；跨机或依赖不完整时不得宣称得到精确全局关键路径或无重叠阶段占比。

### 7.3 完整性与过滤

成功、失败、取消、未完成、恢复后无法确定原始完成时刻、未采样分别标记。
没有实际传输的 path 标为不适用，不伪造零耗时传输样本。
缺少必需层/chunk/贡献者、事件丢失或去重冲突时，不将部分请求纳入完整请求分位数。
局部完整阶段可保留用于排查，但必须标注样本集合，跨阶段对比提供共同完整请求子集。
报告记录 expected/observed/successful/eligible 请求数、拒绝原因和覆盖率，不默默筛掉慢请求或失败请求。
丢样影响范围无法确定时将整轮标为 INCOMPLETE，不仅凭剩余记录形成“完整成功”结论。
采集窗口、请求 ID、输入/输出目标、D rank、K endpoint、batch 可筛选；过滤规则保存进报告。

## 8. 事件身份、时钟与存储

### 8.1 拟议事件字段

| 字段组       | 所需语义                                                                                          |
| ------------ | ------------------------------------------------------------------------------------------------- |
| 采集来源身份 | schema、run_id、process_instance_id、host/boot_id、进程身份、角色、框架/SDK版本；均为静态关联标签 |
| 请求关联     | 外部 request_id、P/D 别名、generation、request attempt                                            |
| 传输关联     | layer、plane、chunk、有序批次、贡献者、path、job/rpc/span/parent ID                               |
| 资源关联     | P/D DP/TP rank、物理 NPU、K endpoint、非敏感 source/MR/region 身份                                |
| 时间         | 开始/结束、clock domain、单位 ns、结束状态、缺失原因                                              |
| 负载         | 实际字节数、逻辑 token、batch_id、batch membership、图模式、有效/填充数量                         |
| 质量         | host/API/device 观察级别、时钟校准误差、采样及丢样状态、配置快照标识                              |

只引用请求执行中已有的稳定身份，不为补齐标签增加资源注册、导入、探测或设备查询。
不序列化 SDK 对象、完整配置、prompt、输出文本、Tensor 或地址表。
原始 payload 不进入采样文件；失败堆栈也要限量，不随每个事件重复保存。

### 8.2 时钟策略

本机阶段使用单调时钟，跨进程先核对 host、boot、clock domain；不同机器 monotonic 时间不直接相减。
采集窗口开始/结束记录单调时间与墙钟映射以及可获得的 PTP/chrony 同步证据，检测漂移和时钟跳变。
工具不在请求路径主动发时钟探测 RPC；外部校准信息可以导入，并保留误差区间。
有可靠同步证据时才定量比较跨机起止；否则按因果边和本地持续时间展示近似对齐，明显标出误差及未对齐状态。
跨机时间差小于同步不确定度时不判定因果倒置或单向网络延迟。

### 8.3 输出与规模控制

启用写盘时拟输出原始 `events-*.jsonl`、运行 manifest 和 checkpoint，按第 3.3 节预算分片及停止；
这些是保留在服务侧的分析中间数据，不要求逐一复制到 Windows。
默认分析输出终端摘要；按需汇总一个 `kvaf-pd-<run_id>.trace.json`，CSV/summary.json 仅作为可选旁路导出，不是查看阶段耗时的前置条件。
分析及 Trace 产物不计入采集写盘预算，单独限制分析内存与导出大小，不能因导出绕过资源预算。
checkpoint 记录入队、落盘、丢弃、错误、未结束 span 和采样覆盖；异常退出留下未闭合状态，不能补造成功结束。
运行文件按 run/进程代次区分，重复拷贝去重，不混合不同进程代次。
大规模数据先按请求/时间窗口筛选，再汇总成单文件；查看器按请求建立索引并按需渲染，不一次创建全部层级 DOM。
若所选范围超过导出或 Windows 可承受预算，明确要求缩小范围或提高显式预算，不静默截断、不自动变成多个交付文件。

### 8.4 单 Trace 文件契约

采用 Chrome Trace Event JSON 作为基础格式，文件后缀为 `.trace.json`，含标准 `traceEvents` 数组及工具自有的版本化元数据区。
第一版使用文本 JSON，不要求 Windows 安装解压、数据库、Python 或 vLLM 环境；实际查看器兼容性由 M5 验证，不先宣称已支持。

| 文件内数据     | 所需内容                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------- |
| 时间事件       | 实际持续动作、瞬时里程碑、可验证的请求因果关联，覆盖导出请求的层/chunk/贡献者                 |
| 阶段分组身份   | 主机、角色、进程代次、P/D rank、传输路径、K endpoint 和 lane 映射，避免不同主机 PID 冲突      |
| 原始与展示时间 | 原始 ns、clock domain、映射依据与误差；标准事件时间转换为微秒，不能将 ns 原数直接当作标准时间 |
| 统计摘要       | t1/t2 四组、阶段及可得的请求 E2E/TTFT 的 mean/P90/P99/有效 N，与导出请求集合一致              |
| 配置与完整性   | 负载目标/实际、采样配置、筛选条件、来源清单、拒绝/缺失/丢样计数、未闭合事件及 schema/工具版本 |

持续动作使用标准 duration 事件，里程碑使用 instant 事件；未知终点不补 duration，不把统计分位数写成执行事件。
同一请求的父子关系及原消息关联保留在事件身份和元数据中；因果 flow 连线须有真实关联且时钟映射允许，不以显示顺序推断。
可靠对齐的主机事件可放在公共时间轴；未可靠对齐的域保留原始本地时间及未对齐标识，由配套查看器在独立本地时间轴展示。
通用查看器的标准事件区只导出可可靠映射的事件；无法映射的事件保存在同一 Trace 的版本化元数据区，不强行归零制造跨机先后关系。
完整的未对齐域查看、质量标识和统计面板由配套离线查看器提供；通用 Chrome Trace/Perfetto 类工具仅作为标准事件区的基础阶段耗时兼容目标。

Trace 必须包含查看所选数据所需的全部证据和摘要，不引用服务器绝对路径下的文件，不要求额外下载原始日志。
导出使用稳定快照和同一筛选集合；缩小导出范围时同步重算摘要，不能附带全量统计伪装成当前子集。
后台采集不承担 Trace 归并；独立导出脚本采用有界处理，在成功完成后发布目标文件，失败时不留下看似完整的 Trace。

## 9. 可视化交互与结果解释

Windows 使用配套的离线 HTML 查看器，通过文件选择或拖入一个 Trace 打开；查看器可随工具单独交付一次，数据交付始终是一个 Trace。
无需在服务上运行绘图页面，无 CDN、在线上传或外部文件依赖；图表和摘要均由该 Trace 提供。

### 9.1 实际阶段耗时

请求视图提供 Proxy/入口、P 调度与计算、P Connector、D 调度与处理、D2D、K DDR endpoint、D Decode 等阶段耗时。
没有 K/设备内部事件时，阶段名称明确写“调用方观察”，不画假设备执行块。

横轴为时间，纵轴为执行阶段或角色；持续动作画 span 色块，里程碑画点/竖线，不把瞬时事件画成有持续时间的操作。
界面分为真实请求时间轴、阶段 mean/P90/P99 统计面板、请求/层/chunk 详情三部分，能够从慢请求定位到慢交互或慢传输。

支持缩放、平移、区间选择、请求/层/chunk折叠、同一请求因果连线、慢段排序和状态过滤。
点击色块查看本段实际耗时、阶段总体 mean/P90/P99、样本量、字节数、身份、等待原因和观察级别，区分当前值与总体分布。
颜色稳定对应计算、控制、等待、D2D、DDR、Commit/发布和缺失/失败，不单凭颜色表示性能异常。

### 9.2 统计与代表请求

报告提供阶段 mean/P90/P99 分组图、t1/t2 四组汇总、按层/卡/K endpoint 对比和可得的 batch 关联。
可选择接近 E2E P50/P90/P99 的真实完整请求查看阶段耗时，标明请求 ID 和实际分位位置。
统计图不把阶段 P99 堆叠成 E2E P99；均值分段示意也要标明重叠和样本集合，不能冒充真实请求轨迹。

CSV/JSON 明细按需导出；Windows 可视化支持导出所选范围 SVG/PNG，静态图保留单位、筛选条件、时钟质量和完整性标识。
输入/输出/batch 目标可在分析入口配置，和实际观测不一致时显示，不静默修改数据或丢弃不匹配样本。

## 10. 性能表现分析与验收

### 10.1 要回答的问题

- Connector 慢在 plan/Ready/回执、线程池、源组锁、D Runtime 锁，还是 SDK 完成等待？
- t1/t2 哪一条决定本请求的 KV 就绪，哪些传输已经与 P Prefill 重叠？
- KV 全部就绪后，D 是否仍长时间等待完成汇总或调度？
- 尾延迟集中在哪层、chunk、D rank、K endpoint 或实际 batch？

一次 trace 是定位证据，不单独证明适配带来多少退化。
使用相同模型/SDK、量化、图/MTP、source 模式、负载和资源预算，比较不采样与采样的吞吐、TTFT、TPOT、E2E 和内存。
再按需要对比明确指定的非 PD 或其他已验证基线；拓扑/数据路径不同的结果单独解释，不直接宣称差异全来自 Connector。
交替重复实验，记录所选请求集合、实际 batch、请求成功/失败/取消率和配置；不把诊断哈希或 profiler 开启后的数据作为低开销基线。

### 10.2 验收项

| 编号 | 条件                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PA01 | 默认关闭、Connector 对象级可插拔；仅真实请求触发且可关联的事件进入采集、统计和阶段耗时，不扩展到请求前的实例阶段，不修改原生核心或新增采样专用设备资源/同步 |

如基线本身不稳定先量化自身波动，发现新分歧则调查，不能仅凭“统计工具不写 KV”宣称精度安全。
请求、取消、失败、长时间运行和关闭插件后的资源行为均纳入交付证据。
